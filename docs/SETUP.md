# Set up Kinderalltag

## 1. Build environment

Use Android Studio with Gradle JDK **17 or 21**, Android SDK Platform **36**, and the SDK build tools Android Studio requests. Select a supported Gradle JDK explicitly. For the command line, set `JAVA_HOME` to that installation and set `ANDROID_HOME` to the Android SDK, or create an ignored `local.properties` containing `sdk.dir=/absolute/path/to/Android/sdk`.

The included Gradle wrapper downloads Gradle and Maven dependencies on the first connected build. The bootstrap JAR is generated by Gradle 7.4.2; the distribution it launches is pinned to 9.6.0.

## 2. Firebase project

1. Create a Firebase project in your own Google account. Leave Google Analytics disabled. Start on the Spark plan; this implementation uses Authentication and Firestore without Cloud Functions or server push.
2. Register Android package **de.kinderalltag**. Obtain signing fingerprints with `./gradlew :app:signingReport` and register the debug SHA-1/SHA-256. Register your release fingerprints before installing release builds.
3. Enable **Authentication → Sign-in method → Google**, choose a support email, then download the updated `google-services.json` into **app/google-services.json**. Google sign-in requires the generated `default_web_client_id` (OAuth client type Web). Re-download the configuration after enabling Google authentication if it was missing.
4. Create a Cloud Firestore **Standard** database in production mode. Choose **europe-west3 (Frankfurt)** at creation. Its location cannot subsequently be changed in place. Authentication and other Google services have their own data handling; selecting Firestore's location does not put every service in that region.
5. Deploy the rules and indexes from the repository. With Firebase CLI installed and authenticated:

   ```sh
   firebase deploy --project YOUR_PROJECT_ID --only firestore:rules,firestore:indexes
   ```

   Alternatively paste `firebase/firestore.rules` into Firestore's Rules editor and publish it. Never enable broad test-mode access.

## 3. Provision the family

The first version has one household with two equal parents. Provisioning is a one-time console operation; the app cannot add its own members.

1. Build with `./gradlew :app:assembleDebug` and install `app/build/outputs/apk/debug/app-debug.apk` on both phones. Each parent signs in with their own Google account. The app displays the account's Firebase user ID while waiting for access. IDs also appear in Firebase Authentication's Users tab.
2. In the Firestore console create these documents. You may need to create the parent `households/family` document with a harmless `label` string; its contents are not used by the app.

   | Document path | Fields |
   | --- | --- |
   | `households/family/members/FIRST_PARENT_UID` | `name` (string): preferred parent name |
   | `households/family/members/SECOND_PARENT_UID` | `name` (string): preferred parent name |
   | `households/family/children/ferdinand` | `name` (string): `Ferdinand` |
   | `households/family/children/johann` | `name` (string): `Johann` |

3. The app observes membership and opens the checklist when access is granted. The stored member name is administrative only; acknowledgement names come from each parent's Google profile.
4. Create your actual tasks in the app. It does not create medication examples or assume times or instructions for them.

**Haushalt** is a built-in section alongside the children. It requires no profile document or manual database initialization. When updating an existing installation, publish the current `firebase/firestore.rules` (or run the rules deployment command above) before saving household tasks: the rules now also allow `childId: "haushalt"`.

Each child has a bear icon inspired by `bear.jpg`. Choose its color under **Einstellungen → Kinder → Name & Bärenfarbe**. Color and name changes sync to both parents. Existing child documents need no manual changes: absent `bearColor` fields default to blue for Ferdinand and rose for Johann. Publish the updated rules before saving colors; they now allow the optional `bearColor` field (`BLUE`, `ROSE`, `GREEN`, `HONEY`, `BROWN`, `PURPLE`).

Removing a membership document revokes future server access. As with any offline app, data previously downloaded to that device may remain in its local cache; removing membership cannot remotely erase an offline phone.

## 3a. Update for appointments and parent responsibility

Publish the current `firebase/firestore.rules` **before** installing the update on both phones. The rules allow family members to read parent names, validate assignments to existing member UIDs, and authorize the two appointment collections. Membership writes remain administrative. Names for responsibility selection come from the `name` fields on the existing member documents.

No database backfill is required: tasks without `responsibleParentId` belong to both parents, and appointment collections are created on the first authorized save. Update both phones before using assignments, since older app versions do not filter reminders by responsibility.

Use **Termine → + Termin** to add appointments. Recurrence supports every 1–1000 days, weeks, months, or years. Select one child, both children, or Haushalt, then choose the responsible parent(s). A shared appointment for both children is one entry. Today shows scheduled appointments and Verlauf shows timestamped actions; Einstellungen is now the gear button in the top bar.

Open a future appointment to edit just that occurrence or this and following occurrences. Single-occurrence changes and existing exceptions are preserved. Started occurrences cannot be edited, but can be deleted and restored. Editing and deletion require connectivity; cached viewing and previously scheduled reminders work offline. All-day appointments start at midnight and cannot be edited after that point.

Each enabled phone receives reminders only for its responsible parent. Timed appointments default to 30 minutes before; all-day appointments default to 09:00 the previous day. These are inexact Android alarms, with the same power-management and synchronization limitations as task reminders.

## 3b. Synchronization recovery, pickers, and calendar files

After changing security rules, publish the complete current `firebase/firestore.rules` in **Firestore Database → Regeln → Veröffentlichen**. The old rules deny the parent roster and appointment collections. The app now names the affected data and distinguishes denied access from offline or malformed data. Use **Erneut versuchen**, or **Einstellungen → Jetzt synchronisieren**, after publication: failed Firestore listeners must be reattached. Detailed codes are logged under `KinderalltagSync`. Cached records and queued acknowledgements are retained during reconnect.

Task/appointment dates and times use native pickers, including optional end dates and multiple task times. History has a date picker too. Values are displayed using the phone's locale and 12/24-hour preference; scheduling still uses Europe/Berlin and database values remain ISO. Optional end dates can be cleared with the remove button.

The home screen starts with a summary card with a plain-text date, task and elapsed-appointment counters, followed by Aufgaben and Termine. Green task and blue appointment progress bars appear beneath their counters, framed by a small sun and crescent moon; empty sections show full progress (nothing outstanding). Rounded green previous/next-day buttons navigate past or future dates, with Zurück zu heute when viewing another day. The yellow add buttons sit side by side. Appointments count as absolviert once their scheduled end has passed; this is a calendar-time summary, not attendance confirmation. **Verlauf** combines task and appointment activity, newest first. Each day has an overview with a colored rectangle per event and matching markers beside its timestamped detail rows. Task completions are green; corrections coral; task edits and appointment changes blue; new appointments yellow; cancellations burgundy. The 90-day backward navigation remains at the bottom. **Termine** starts with an introduction box whose family-life message changes whenever you return to the tab. Both **Aufgaben** and **Termine** end with a navigation card. Aufgaben shows up to 90 upcoming task definitions per page, sorted by the next actual execution date and time, with a range such as “1–90 von 125”; the arrows page by 90 tasks. Filters restart the task list at the first page. Future tasks remain visible regardless of how far away they start; ended tasks are excluded. Termine keeps consecutive 90-day periods from today, with **Ab heute anzeigen** returning to the first period. Paused tasks remain accessible through **Pausierte Aufgaben anzeigen** so they can be resumed. Calendar files can still be received through Android sharing/opening; the agenda has no file-import button or extra “Kommende Termine” heading.

To send an appointment, open its details and select **Diesen Termin teilen**. This shares that occurrence as an `.ics` file with title, time, location, notes, and the recipient label as a calendar category. Firebase member IDs and parent assignments are omitted. Recurring appointments are shared as the selected occurrence, not the whole series.

Kinderalltag registers for opening/sharing `text/calendar`, `application/ics`, `application/icalendar`, and `application/x-ical` files. Other apps must share an actual calendar file; arbitrary text or web calendar links are not interpreted. The file-picker import also accepts generically typed files and validates their contents.

Incoming appointments are kept privately while signing in and must be reviewed before saving. Choose the child/household and responsible parent(s) in the review editor; imported appointments initially target Haushalt and both parents. Saved records use the normal authenticated appointment transaction. Canceling the editor leaves the import pending; use Prüfen or Überspringen to continue. Multiple events are reviewed one at a time; exact duplicates in the incoming files are collapsed and existing similar records require confirmation before creating another copy.

Imports are limited to 1 MB and 100 events. Single-day timed/all-day events and simple day/week/month/year intervals are supported. Unsupported multi-day events, multi-weekday rules, custom time zones, and recurrence exceptions are reported. Month-end, foreign-zone recurrence, missing-end-time, and reminder adjustments require acknowledgement in the review. Imported series are reviewed as copies, not live subscriptions to external calendars.

## 4. Signed APK for everyday use

Generate a dedicated release key locally (passwords are requested interactively):

```sh
keytool -genkeypair -v -keystore family-release.jks -alias kinderalltag -keyalg RSA -keysize 3072 -validity 10000
```

Copy `keystore.properties.example` to `keystore.properties`, fill in the local key path and passwords, and keep both files private. Register the release certificate fingerprints in Firebase:

```sh
keytool -list -v -keystore family-release.jks -alias kinderalltag
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleRelease
```

With signing configured, the signed APK is **app/build/outputs/apk/release/app-release.apk**. Without signing configuration, a release build is unsigned and cannot be installed directly. Transfer the signed APK to both phones and allow installation from the transfer app, or use `adb install -r PATH_TO_APK`.

Back up the signing key and passwords securely. Future updates need the same application ID and key, plus a larger `versionCode`. Android will not update a debug-signed installation with your release key: uninstall the debug build first, after pending changes have synchronized, and sign in again. Synced household data remains in Firestore.

## 5. Notifications

Enable reminders in Einstellungen on each phone separately and accept Android's notification permission. Channel settings can also disable notifications in Android system settings. Opening a task displays the latest locally available status; an offline banner identifies cached data.

Reminders use inexact local alarms and require no push server. Android power management may delay them. Force-stopping the app suppresses background delivery until it is opened again. A completion cancels the other phone's reminder after that phone receives the update; instant cancellation while it is offline or suspended is not guaranteed. Existing schedules are cached for seven days; open the app periodically to synchronize and replenish them.

## Troubleshooting Google sign-in

If sign-in fails, filter Logcat for `KinderalltagAuth`. The app logs the failing stage and exception without logging credentials. A missing `default_web_client_id` means the bundled Firebase configuration lacks the required Web OAuth client.

1. In Firebase Project settings, select Android app `de.kinderalltag`. Register the **debug SHA-1 and SHA-256** from `./gradlew :app:signingReport`; each development machine may have a different debug key.
2. In Authentication → Sign-in method, enable **Google** and choose a support email.
3. Download a **new** `google-services.json` from Project settings and replace `app/google-services.json`. For this package, its `oauth_client` array must contain a `client_type: 3` entry (Web client). The Android OAuth client uses the package name and signing SHA-1. Do not invent client IDs or put an Android client ID in place of the Web client ID.
4. Rebuild and update the installed APK: `./gradlew :app:assembleDebug :app:installDebug`. No data reset or keystore regeneration is necessary.
5. If it still fails, capture the `KinderalltagAuth` exception from a fresh attempt. A Google Play services `FlagStore` / `providerinstaller` certificate warning alone does not identify which sign-in stage failed.

The existing Firebase configuration may build successfully even when Google OAuth clients are absent; successful APK assembly does not verify Google authentication setup.

For `GetCredentialCancellationException: [16] Account reauth failed` during account selection, do not assume the user canceled. First check **Google Cloud Console → Google Auth Platform → Clients** in the same project as Firebase. Google sign-in needs both a Web client and an **Android** client matching `de.kinderalltag` and the installed APK's SHA-1. A Web client alone fixes the missing resource but does not register the Android app's identity. Registering only SHA-256 is insufficient for this Android OAuth client.

If the Android client is absent, add the debug SHA-1 to the Android app in Firebase Project settings, then verify the Android client was created. If necessary, create the Android client in Google Cloud using that exact package/SHA-1 pair. Download the updated Firebase configuration and rebuild. An absent `client_type: 1` entry in a downloaded configuration is a reason to verify the console registration, rather than proof of the console's current state.

If both clients already match, check for a Google-account reauthentication prompt on the phone and capture the device model, Android/Play services versions, and whether a second Google account reproduces the error. Do not automatically retry canceled credential requests or remove the phone's account as a first troubleshooting step.

## Settings and live family notifications

Einstellungen groups the account/synchronization status, notification preferences, child profiles, family time and app information into cards. **Über Kinderalltag → Impressum** displays the supplied publisher/contact details; email and website buttons open the phone's selected apps, and the details can be copied.

**Erinnerungen** retains the existing scheduled reminders. **Neue Aufgaben** and **Neue Termine** are separate, initially disabled switches for additions by the other parent. Android notification permission is requested for whichever switch is enabled; denial leaves that switch off. **Android-Benachrichtigungen verwalten** opens the system controls. Live notification choices are stored per account on each phone.

Live notifications use the app's existing Firestore subscription while its process is running and connected. They do not provide closed-app push delivery and need no extra Firebase backend. A first complete server snapshot establishes a silent baseline, so installation, restart and signing in do not replay history. Own additions, task edits/pauses/resumes, appointment edits/cancellations and series splits do not trigger “new” alerts. Events observed while a switch is off are consumed rather than queued. Cached, incomplete, pending or error states wait for server confirmation; reconnecting within the same process can then report new additions. Appointment alerts use the immutable ADDED activity records, so both phones should run the updated app.

Notification taps open Aufgaben or Termine. Disabling scheduled reminders clears only that reminder channel, keeping family-activity alerts independent. Signing out or losing family access clears live notices and resets their baseline. Android may still delay delivery or stop the process; reopening establishes a new silent baseline.

**Darstellung → Alltagsgedanken anzeigen** controls the rotating introductions on **Aufgaben**, **Termine**, **Einkaufsliste** and **Geschenkideen** together. It is off by default and remembered on this phone. Other page content remains available when the introductions are hidden.

## Save an appointment in a phone calendar

Open a Termin and tap **Im Kalender speichern**. Kinderalltag opens an installed calendar app's event editor using Android's standard INSERT action. Choose the destination calendar/account, review the prefilled title, date/time, location and notes, select any calendar reminder, and save there. Calendar apps that handle this action, such as Google Calendar or Samsung Calendar, can receive the copy; actual behavior must be checked on the phones in use. No new Firebase rules, setup or calendar permissions are needed.

The action copies **only the selected occurrence**, using its current details after any move/edit. It does not export recurrence or deletions/exceptions as a new series. The calendar copy is independent: later edits/deletions are not synchronized, and repeating the action can create duplicates. Kinderalltag cannot confirm that the external editor saved the event, so it never marks an appointment as exported or saved. If no compatible calendar app is installed, the app offers a message pointing to the existing **Teilen** action.

All-day dates use UTC midnight boundaries with an exclusive next-day end; timed appointments retain their Berlin instants/timezone. The external editor controls its own display and reminder defaults. This follows the [Android Calendar Provider intent workflow](https://developer.android.com/identity/providers/calendar-provider).

Bauernhof combines cream, field green, wheat yellow and barn red with tractors, grain, a combine harvester, a round baler, cows, pigs and a barn. Magische Welt adds soft lilac, pink and mint with unicorns, fairies, a princess, elves, a magic wand and an enchanted castle. All artwork is drawn locally with Compose Canvas; the animal reference image is not packaged in the app.

Children keep their existing color choice: Garden shows the original bear, Play a plush bear, and Space a helmeted astronaut bear. Animals adds a woodland bear accent while retaining the configured fur color; Vehicles adds a yellow hard hat, Nature a flower by the ear, Farm a straw hat, and Magic a little crown. The menu symbol next to Kinderalltag becomes a sprout, blocks, planet, fox, tractor, tree, farm tractor, or unicorn and opens the same pages. Task status colors, destructive red actions and yellow progress symbols keep their meanings. The launcher icon follows the selected theme: the original Garden logo, toy blocks, a planet, a fox, a green tractor, a tree, a red farm tractor, or a unicorn. Each is an adaptive icon with a matching Android 13+ monochrome variant. Selection switches local launcher aliases immediately and is reconciled on process startup; launcher caches may delay the visible refresh. Existing pinned shortcuts may need to be re-added on some launchers. The monochrome worm notification icon remains unchanged. These are eight light themes; they do not follow Android dark mode.
