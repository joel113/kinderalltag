# Set up Kinderalltag

## 1. Build environment

Use Android Studio with Gradle JDK **17 or 21**, Android SDK Platform **36**, and the SDK build tools Android Studio requests. Gradle 8.13 does not run with JDK 25/27; select a supported JDK explicitly. For the command line, set `JAVA_HOME` to that installation and set `ANDROID_HOME` to the Android SDK, or create an ignored `local.properties` containing `sdk.dir=/absolute/path/to/Android/sdk`.

The included Gradle wrapper downloads Gradle and Maven dependencies on the first connected build. The bootstrap JAR is generated by Gradle 7.4.2; the distribution it launches is pinned to 8.13.

## 2. Firebase project

1. Create a Firebase project in your own Google account. Leave Google Analytics disabled. Start on the Spark plan; this implementation uses Authentication and Firestore without Cloud Functions or server push.
2. Register Android package **de.kinderalltag**. Obtain signing fingerprints with `./gradlew :app:signingReport` and register the debug SHA-1/SHA-256. Register your release fingerprints before installing release builds.
3. Enable **Authentication → Sign-in method → Google**, choose a support email, then download the updated `google-services.json` into **app/google-services.json**. Google sign-in requires the generated `default_web_client_id` (OAuth client type Web). Re-download the configuration after enabling Google authentication if it was missing.
4. Create a Cloud Firestore **Standard** database in production mode. Choose **europe-west3 (Frankfurt)** at creation. Its location cannot subsequently be changed in place. Authentication and other Google services have their own data handling; selecting Firestore's location does not put every service in that region.
5. Deploy the rules and indexes from the repository. With Firebase CLI installed and authenticated:

   ```sh
   firebase deploy --project YOUR_PROJECT_ID --only firestore:rules,firestore:indexes
   ```

   Alternatively paste `firebase/firestore.rules` into Firestore's Rules editor and publish it. Never enable broad test-mode access.

## 3. Provision the family

The first version has one household with two equal parents. Provisioning is a one-time console operation; the app cannot add its own members.

1. Build with `./gradlew :app:assembleDebug` and install `app/build/outputs/apk/debug/app-debug.apk` on both phones. Each parent signs in with their own Google account. The app displays the account's Firebase user ID while waiting for access. IDs also appear in Firebase Authentication's Users tab.
2. In the Firestore console create these documents. You may need to create the parent `households/family` document with a harmless `label` string; its contents are not used by the app.

   | Document path | Fields |
   | --- | --- |
   | `households/family/members/FIRST_PARENT_UID` | `name` (string): preferred parent name |
   | `households/family/members/SECOND_PARENT_UID` | `name` (string): preferred parent name |
   | `households/family/children/ferdinand` | `name` (string): `Ferdinand` |
   | `households/family/children/johann` | `name` (string): `Johann` |

3. The app observes membership and opens the checklist when access is granted. The stored member name is administrative only; acknowledgement names come from each parent's Google profile.
4. Create your actual tasks in the app. It does not create medication examples or assume times or instructions for them.

**Haushalt** is a built-in section alongside the children. It requires no profile document or manual database initialization. When updating an existing installation, publish the current `firebase/firestore.rules` (or run the rules deployment command above) before saving household tasks: the rules now also allow `childId: "haushalt"`.

Each child has a bear icon inspired by `bear.jpg`. Choose its color under **Einstellungen → Kinder → Name & Bärenfarbe**. Color and name changes sync to both parents. Existing child documents need no manual changes: absent `bearColor` fields default to blue for Ferdinand and rose for Johann. Publish the updated rules before saving colors; they now allow the optional `bearColor` field (`BLUE`, `ROSE`, `GREEN`, `HONEY`, `BROWN`, `PURPLE`).

Removing a membership document revokes future server access. As with any offline app, data previously downloaded to that device may remain in its local cache; removing membership cannot remotely erase an offline phone.

## 4. Signed APK for everyday use

Generate a dedicated release key locally (passwords are requested interactively):

```sh
keytool -genkeypair -v -keystore family-release.jks -alias kinderalltag -keyalg RSA -keysize 3072 -validity 10000
```

Copy `keystore.properties.example` to `keystore.properties`, fill in the local key path and passwords, and keep both files private. Register the release certificate fingerprints in Firebase:

```sh
keytool -list -v -keystore family-release.jks -alias kinderalltag
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleRelease
```

With signing configured, the signed APK is **app/build/outputs/apk/release/app-release.apk**. Without signing configuration, a release build is unsigned and cannot be installed directly. Transfer the signed APK to both phones and allow installation from the transfer app, or use `adb install -r PATH_TO_APK`.

Back up the signing key and passwords securely. Future updates need the same application ID and key, plus a larger `versionCode`. Android will not update a debug-signed installation with your release key: uninstall the debug build first, after pending changes have synchronized, and sign in again. Synced household data remains in Firestore.

## 5. Notifications

Enable reminders in Einstellungen on each phone separately and accept Android's notification permission. Channel settings can also disable notifications in Android system settings. Opening a task displays the latest locally available status; an offline banner identifies cached data.

Reminders use inexact local alarms and require no push server. Android power management may delay them. Force-stopping the app suppresses background delivery until it is opened again. A completion cancels the other phone's reminder after that phone receives the update; instant cancellation while it is offline or suspended is not guaranteed. Existing schedules are cached for seven days; open the app periodically to synchronize and replenish them.

## Troubleshooting Google sign-in

If sign-in fails, filter Logcat for `KinderalltagAuth`. The app logs the failing stage and exception without logging credentials. A missing `default_web_client_id` means the bundled Firebase configuration lacks the required Web OAuth client.

1. In Firebase Project settings, select Android app `de.kinderalltag`. Register the **debug SHA-1 and SHA-256** from `./gradlew :app:signingReport`; each development machine may have a different debug key.
2. In Authentication → Sign-in method, enable **Google** and choose a support email.
3. Download a **new** `google-services.json` from Project settings and replace `app/google-services.json`. For this package, its `oauth_client` array must contain a `client_type: 3` entry (Web client). The Android OAuth client uses the package name and signing SHA-1. Do not invent client IDs or put an Android client ID in place of the Web client ID.
4. Rebuild and update the installed APK: `./gradlew :app:assembleDebug :app:installDebug`. No data reset or keystore regeneration is necessary.
5. If it still fails, capture the `KinderalltagAuth` exception from a fresh attempt. A Google Play services `FlagStore` / `providerinstaller` certificate warning alone does not identify which sign-in stage failed.

The existing Firebase configuration may build successfully even when Google OAuth clients are absent; successful APK assembly does not verify Google authentication setup.

For `GetCredentialCancellationException: [16] Account reauth failed` during account selection, do not assume the user canceled. First check **Google Cloud Console → Google Auth Platform → Clients** in the same project as Firebase. Google sign-in needs both a Web client and an **Android** client matching `de.kinderalltag` and the installed APK's SHA-1. A Web client alone fixes the missing resource but does not register the Android app's identity. Registering only SHA-256 is insufficient for this Android OAuth client.

If the Android client is absent, add the debug SHA-1 to the Android app in Firebase Project settings, then verify the Android client was created. If necessary, create the Android client in Google Cloud using that exact package/SHA-1 pair. Download the updated Firebase configuration and rebuild. An absent `client_type: 1` entry in a downloaded configuration is a reason to verify the console registration, rather than proof of the console's current state.

If both clients already match, check for a Google-account reauthentication prompt on the phone and capture the device model, Android/Play services versions, and whether a second Google account reproduces the error. Do not automatically retry canceled credential requests or remove the phone's account as a first troubleshooting step.
